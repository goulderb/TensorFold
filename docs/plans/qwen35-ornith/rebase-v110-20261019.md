## The two checkpoint encodings keep their own execution paths

The upstream `qwen3_5/cuda.zig`, `cuda_engine.zig`, and `cuda_weights.zig` are
byte-identical to the new trunk base. They remain the MLX implementation and
retain the native MoE registration, MTP, vision, cache, and shared lane APIs.

The ModelOpt proof uses `modelopt_cuda.zig`, `modelopt_cuda_engine.zig`, and
`modelopt_cuda_weights.zig` in the same family directory. Its FP8 dense weights,
NVFP4 experts, and serial layer split need a format and state port before they
can use the generic MLX engine. This rebase preserves that proof without changing
its arithmetic. It shares the current upstream config parser through the
`qwen35` module, rather than importing the same parser into two Zig modules.
The `qwen35_cuda` build alias still serves the existing probes and adapter.

The native dispatcher reads checkpoint encoding before selecting a Qwen backend.
ModelOpt markers select strict ModelOpt validation even when the checkpoint is
malformed. Other Qwen encodings continue into the upstream registry. The catalog
has one `qwen3_5_moe` entry containing both upstream formats and
`modelopt-mixed-nvfp4`. ModelOpt explicitly refuses FP8 KV. Its shared Host now
initializes `drafted.Served` before teardown.

`qwen35_ops` is registered in v1.1's `zig/build/cuda_kernels.zig` catalog with
the original glue flags. The shared `qlinear`, `experts`, `ck`, and
`nvfp4_experts.cu` files remain byte-identical to the new trunk, including its
new expert variants. Existing diagnostic build targets and source-pin options
are retained. New fatbins and device qualification are still required.
